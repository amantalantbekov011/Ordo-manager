# ORDO Manager: хранение и размещение

## Принятая схема

- Рабочая копия разработчика: `C:\Users\User\Documents\Codex\Планировщик`.
- Главный источник кода и истории изменений: приватный GitHub-репозиторий `amantalantbekov011/Ordo-manager`.
- Исходные архивы и референсы: `materials/` в рабочей копии. Архивы не участвуют в сборке приложения.
- Секреты и пароли: только переменные окружения облачной платформы и локальный `.env`; никогда не Git.
- Рабочие данные: PostgreSQL. Файл `data/db.json` допустим только для локального прототипа.

## Окружения

1. **Local** — разработка и автоматические тесты на компьютере.
2. **Staging** — закрытая тестовая версия, автоматически обновляемая из ветки `develop`.
3. **Production** — рабочая версия из защищённой ветки `main`; выкладка только после тестов.

## Рекомендуемое облако

На этапе MVP: **Render Web Service + Render PostgreSQL**. Причины: прямое подключение приватного GitHub, автоматическая выкладка после push, единая панель приложения и БД, HTTPS и управляемые резервные копии на платных тарифах.

Файловая система облачного веб-сервиса временная, поэтому задачи, пользователи и события должны храниться в PostgreSQL, а вложения — в S3-совместимом объектном хранилище. Не следует развивать текущий `data/db.json` как производственную базу.

## Целевая архитектура

- Web: адаптивный интерфейс, затем PWA при необходимости.
- API: Node.js LTS, структурированные маршруты и централизованная проверка данных.
- Database: PostgreSQL с миграциями и журналом изменений.
- Auth: хешированные пароли, роли, срок жизни сессии, защищённые cookies.
- Files: S3-совместимое хранилище с ограниченными ссылками.
- CI/CD: тесты на каждый pull request; staging автоматически; production после подтверждения.
- Backup: point-in-time recovery базы плюс отдельный регулярный экспорт.

## Ближайшие этапы

1. Стабилизировать текущий MVP: кодировка, ошибки, тесты, безопасность и мобильная верстка.
2. Уточнить роли, процессы задач, уведомления и обязательные поля.
3. Перенести данные в PostgreSQL и подготовить staging.
4. Провести приёмочное тестирование с директором и помощником.
5. Запустить production, мониторинг и резервное копирование.
# SaaS-архитектура v3

ORDO Manager использует обязательный `companyId` для компаний, пользователей и всех бизнес-сущностей. Сервер никогда не принимает компанию из клиентского запроса: область данных определяется только по защищённой серверной сессии. Регистрация создаёт компанию, администратора тарифа START и головной офис. Существующие записи автоматически мигрируют в `company_ordo` (ОРДО Трейд).

Сессии сохраняются как SHA-256-хэши токенов, пароли — через `scrypt` с индивидуальной солью. API проверяет роль, компанию связанных сущностей и Origin. Добавлены ограничение попыток входа, CSP и защитные HTTP-заголовки.

Текущая файловая база подходит для одного процесса Render с постоянным диском. Перед коммерческим масштабированием на несколько экземпляров требуется PostgreSQL, транзакционные миграции, объектное хранилище вложений, SMTP-провайдер и внешний платёжный провайдер.
